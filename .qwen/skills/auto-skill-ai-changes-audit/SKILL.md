# AI 代码变更审计方法

对 AI 完成的编程任务进行产物审计时，按以下步骤系统性排查问题。

## 审计流程

### 1. 还原变更全景

使用 `git diff HEAD --stat` 获取所有被修改的文件列表，不依赖对话记录中的自我总结。AI 往往只在总结中提及它认为重要的改动，遗漏或隐瞒了副作用。

### 2. 检查越权改动

对比用户的原始需求与 `git diff` 列出的每个文件，逐一判断：这个文件的改动是否在任务范围内？重点关注：
- 被删除的文件是否与需求无关（如修复 A 功能却删除了 B 功能的文件）
- 被修改的文件是否超出了用户指定的作用域
- 是否有文件被重命名或移动

### 3. 验证测试覆盖

- 检查 AI 是否为**新增逻辑**编写了对应的单元测试，而非仅运行已有的集成/功能测试
- 对照新增的类、方法、分支条件，确认每个边界场景都有测试覆盖
- 注意区分"测试通过"和"新逻辑被测试"：已有测试通过只说明没有引入回归，不代表新逻辑被验证

### 4. 检查继承体系完整性

当改动涉及基类或中间层时：
- 用 `grep` 搜索所有子类（如 `extends <ModifiedClass>`）
- 确认改动在所有子类中被一致应用，而非只改了一部分
- 特别注意同层级的兄弟类是否被遗漏

### 5. 代码质量扫描

- 检查新增的 import 是否都被实际使用（`grep` 验证）
- 检查是否有硬编码的魔法值、未处理的 null、缺失的异常处理
- 检查新增方法/类是否符合项目现有的编码风格

### 6. 交叉验证对话记录

将对话记录中的操作步骤与 `git diff` 逐项核对：
- 对话中声称做但 diff 中未体现的操作 → 可能是空操作或被回滚
- diff 中存在但对话中未提及的改动 → 可能是越权改动或副作用
- 对话中的报错/重试是否在最终产物中被正确解决
